# Required editorial photograph

Read target docs/EDITORIAL.md, docs/CONTENT_MODEL.md, [the visual constitution](../../../docs/editorial/VISUAL_CONSTITUTION_V1.md), [the illustration guide](../../../docs/editorial/ILLUSTRATION_SYSTEM_V1.md) and the story/ledger first. Never change research classifications. For new editions from 2026-10-22, `mode=none` is not a valid publication choice: withhold the story if no image can pass all gates. Historical image-free stories remain backfill work. A declared generated image requires the complete review and asset; do not silently change mode after a generation failure.

Generate only for a verified, selected, factually stable story. Follow the visual constitution's **Editorial Science Photography** direction: credible, cinematic, human-centred, photojournalism-inspired context without inventing documentary evidence. Propose three distinct written photographic concepts before new generation, then choose one with a story-specific rationale. Record why the others were rejected. Consider believable staged clinicians, anonymous adult patients when genuinely justified, researchers collaborating, relevant clinical workflows, expressive environmental portraits, conceptual still life or a tactile close-up. People, faces, directional light and richly layered scenes are allowed when their juxtaposition with the headline remains truthful. Reject interchangeable portraits, desk-and-device stock imagery, fake medical drama and fictional study-specific details. Do not require white desks, teal props, soft light, blanket absence of people or central placement. Preserve the constitution's medical, privacy and illustrative-caption safeguards; never invent clinical evidence or study hardware.

Use the existing strict brief fields: actual story ID, verified context, chosen visual idea, placement and crop. Put the editorial point, meaningful visual relationship, composition/focal point, lighting, human-presence limits, staged/illustrative disclosure, headline-photo inference risks, and story-specific anti-cliches into constraints. Request **one standalone, text-free photograph**, not a collage, website/card layout or screenshot. Keep headlines, dates, summary text, visual labels and illustrative captions in the Astro presentation layer. Include all material instructions in the exact final brief; do not add unsupported fields to the CLI schema. Compare up to five recent approved target images and the current edition's candidates for repeated compositions; record actual compared IDs or unavailable access.

Fix final article bytes, image path, alt text and review path before computing the exact-source SHA-256. Hash exact docs/EDITORIAL.md bytes for policy_sha256 and exact brief bytes for brief_sha256. The review is separate from the article to avoid a self-referential source hash. Target review version is healthtech-1.0; do not copy a source-publication v1.3 approval or identity.

Before generating or reusing, run `npm run illustration:decision -- --story <id> --brief <local-brief.json> --generator-surface <actual-tool> --candidate-count <actual-count> --json` using the brief format in the illustration guide. It is read-only; `NONE` is reserved for historical pre-cutover stories, `GENERATE` is not an approval and `REUSE` still requires normal review/validation. Invalid input blocks the decision.

Compute generation_key as SHA-256 over UTF-8 JSON.stringify of `[story_id, story_source_sha256, brief_sha256, policy_sha256, version, candidate_count, generator, model_snapshot]` using the same ordered array as the validator. Use null for an unavailable model snapshot, never a guessed model name. Reuse only when identity, review, asset bytes and crop remain valid. A retry alone does not justify regeneration.

Start with one actual candidate from the chosen concept. Optionally build a comparison sheet with `npm run illustration:contact-sheet -- --story <id> --out <new.png> --crop <crop> <candidate.webp>` and any real `--reference` inputs; the sheet does not write an approval. Review unsupported medical implication first, including **the photo next to the actual headline and lead**; then real article/listing crops, contrast, alt text and illustrative captions. Make sure fictional scenes are not presented as actual researchers, patients, institutions, devices, evidence or measured outcomes. Apply all four editorial gates in the visual constitution: specificity, meaningful human/story relevance, thumbnail clarity and variety. A strong human-centred scene may pass without a literal mechanism diagram; visual drama never overrides a factual mismatch. Reject a failure even when the technical checks pass. Revise the cause before regenerating and record the real candidate count; never retry unchanged prompts to chase an aesthetic pass.

Save accepted WebP bytes under public/images/stories/<story-id>.webp and a review under docs/editorial/illustrations/reviews/<story-id>.json. Record actual candidate count, generator, asset hash, crop, real reviewer/type/time, unsupported_medical_implication=false and crop_passed=true only after those checks actually occur. Put concept selection, comparisons and pass/fail reasons for each editorial gate in the PR body, keyed to story ID and final asset SHA-256. Do not add aesthetic fields to the strict JSON review or claim CI proves visual quality. Reuse still requires this editorial gate; a matching generation key is not aesthetic approval.

The strict review schema and illustration validator define exact field names. Use binary-safe blobs or git commits. Run npm run illustration:check -- docs/editorial/ledgers/YYYY-MM-DD.json. Report generation/asset/access failures as blockers for that story. Never invent a review, transform a failed candidate into a pass, publish factual charts with generated data, or invoke this workflow for watch/rejected items.
